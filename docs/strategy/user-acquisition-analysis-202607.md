# ユーザー獲得分析（2026-07-04 時点スナップショット）

GA（Web訪問者）と本番DB（実登録）を突き合わせた獲得状況の分析。
「GAは伸びているのに実感が伴わない＝微妙に加工傾向がある」という仮説の検証記録。

> 注意: 本ドキュメントの GA / PostHog の数値は 2026-07-04 取得時点のスナップショット。
> 最新値は都度 MCP で取り直すこと。**判断のグラウンドトゥルースは本番DB（users テーブル）** とする。
> 7月は 1〜4日の部分データ。GA の当日（7/4）も未確定。

## 結論

**GA の新規ユーザー（Web訪問者）は右肩上がりだが、実際の登録数は 5月（575）をピークに 6月（429, -25%）へ減少に転じている。**
月次サマリーの「6月 +64%」という見た目と、プロダクトの実態が乖離している。これが「加工傾向」の正体。

- GA と実登録の **相関が崩れた**：訪問者は増え続けるのに登録が減っている。
- 6月は **獲得も初期リテンションも同時に悪化**（登録 -25%、翌日以降再訪率 53%→43%）。
- 4月に Apple/Google のソーシャルログインが立ち上がり、4〜5月の急伸を牽引 → その効果が 6月に一巡した可能性が高い。

## 打ち手の方向性（仮説）

1. **SEO流入の質を確認**：Search Console で 6月に増えたクエリ/LPを特定。情報収集目的の記事流入が増え、登録意図の低い読者が混ざっている可能性。登録動線のあるページへの流入比率を見る。
2. **ソーシャルログイン導入バンプの一巡**：4月の押し上げが剥落した後の「地力」が現状値。恒常的な獲得施策（招待・チーム機能経由の口コミ）が必要。
3. **登録転換率の回復**：5月に 38% まで上がった転換率を再現できれば、GAの訪問者数（月2,500）でも登録は倍増余地。LP→登録のファネルを PostHog で計測（現状 App Installed→sign up 約27%）。
4. **7月フル月をウォッチ**：現ペースだと 7月は初の前月割れの可能性。要確認。

## 検証に使ったSQL（すべて読み取り専用）

`created_at` は UTC 保存の `timestamp without time zone`。JST集計は `AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tokyo'`。

```sql
-- ① 月次の実登録数
SELECT
  to_char(created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tokyo', 'YYYY-MM') AS month_jst,
  COUNT(*)                                         AS signups,
  COUNT(*) FILTER (WHERE confirmed_at IS NOT NULL) AS confirmed,
  COUNT(*) FILTER (WHERE deleted_at IS NOT NULL)   AS later_deleted
FROM users
WHERE created_at >= '2025-12-31 15:00:00'
GROUP BY 1 ORDER BY 1;

-- ② 直近の日次登録
SELECT (created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tokyo')::date AS day_jst,
       COUNT(*) AS signups
FROM users WHERE created_at >= '2026-05-31 15:00:00'
GROUP BY 1 ORDER BY 1;

-- ③ 登録経路の内訳
SELECT to_char(created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tokyo', 'YYYY-MM') AS month_jst,
       provider, COUNT(*) AS signups
FROM users WHERE created_at >= '2025-12-31 15:00:00'
GROUP BY 1, 2 ORDER BY 1, 3 DESC;

-- ⑤ 初期リテンション近似
SELECT to_char(created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tokyo', 'YYYY-MM') AS month_jst,
       COUNT(*) AS signups,
       COUNT(*) FILTER (WHERE last_login_at > created_at + INTERVAL '1 day') AS returned_after_day1
FROM users WHERE created_at >= '2025-12-31 15:00:00'
GROUP BY 1 ORDER BY 1;
```

## ツールページ→登録 ファネル実測（2026-06）

### 重要な前提：このファネルは PostHog では測れない

- 接続中の PostHog は **「BUZZ BASE mobile」プロジェクトで、モバイルアプリのイベントのみ**を保持。`$current_url` 等のWebプロパティは存在せず、`/tools/era`（Webページ）の閲覧も web `sign up` も入っていない（PostHog の `sign up completed` 75件はアプリ内登録のみ）。
- **Webフロント（front/）は GA4（gtag）で計測**（`app/lib/analytics.ts` の `trackEvent`）。PostHog は未導入。
- したがって **ツールページ→登録の実測は GA4 で行う**。幸いツールページには計測が実装済み：
  - 各ツールの結果カード: `generate_lead`（`source_tool` 付き）
  - 計算フォーム/CTA: `app_store_click`（`tool` / `cta_location` 付き）
  - 登録完了: `sign_up`（`method` 付き）
  - `source_tool` `tool` `cta_location` `method` は GA カスタムディメンション登録済み。

### 実測ファネルの結論

- **ツール系ページに約2,000人が来て、「アプリへ」CTA（app_store_click, tool付き）は14回、`generate_lead` は2回しか発火していない。ツール訪問者のCTAエンゲージメントは概ね1%未満。**
- ツールページからの登録転換は **実質ゼロ**。GAの巨大な流入（月2,500新規）は、この動線で登録に結びついていないことがイベントレベルで裏付けられた。
- **ボトルネックはトラフィックではなく、ツールページのCTA/導線設計**。ここが唯一かつ最大の伸びしろ。

### 計測上の限界と注意（要認識）

1. **cross-device の壁**：ツールページはWeb、実際の登録の主流はモバイルアプリ（Apple 196 / Google 150）。ユーザーは Web→App Store→アプリ内登録 の順で、**GAはApp Store以降を追跡できない**。GAで測れるのは「App Storeへ送る意思＝app_store_click」まで。完全な web→アプリ登録の追跡には install referrer / deferred deep link + モバイル計測が必要。
2. **計測の取りこぼし（データ品質）**：6月の登録は GA `sign_up` 29、PostHog `sign up completed` 75 に対し、**DB実登録は429**。両分析基盤とも大幅に過少計上。KPIは必ずDBを正とし、分析基盤の数値は相対比較・行動分析用途に限定する。
3. **パラメータ命名の不統一**：結果カードは `generate_lead({source_tool})`、計算フォームは `app_store_click({tool})` と別キー。ツール横断の集計時は両方を見る必要がある。統一が望ましい。

### 打ち手（実測を踏まえ更新）

1. **ツールページのCTA改善（最優先・低コスト）**：計算結果直後に「この成績をアプリで記録・共有」CTAを主役級に配置。現状 `generate_lead` ≈0 は、CTAが弱いか目立たない証拠。A/Bで文言・位置・アプリ誘導を検証。
2. **転換の可視化を1プロジェクトに寄せる**：front/ に posthog-js を導入し、Webの pageview / CTA / sign_up を PostHog に集約すれば、ツールページ→登録の真のファネルが1画面で測れる（現状はGA分散計測）。
3. **登録イベントをサーバー側（Rails）から発火**：user 作成時に provider 付きで単一の分析シンクへ送れば、DB(429)と分析基盤の乖離が解消し、獲得の真実を1つの数値で追える。
4. **app_store_click の tool パラメータを全ツールで必ず付与**し、ツール別のApp Store送客数をKPI化する。
