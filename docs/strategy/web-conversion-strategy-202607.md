# Web流入コンバージョン戦略（2026-07 / 深堀り版）

Webからの流入（buzzbase.jp、月約2,500新規・大半がSEO）を登録・アクティブ化へ変換するための構造的戦略。
表層の「CTA改善」ではなく、その2〜3層下（ファネル段階の不一致 / cross-device の断絶 / 意図のミスマッチ）から設計する。

> 前提データ（2026-06 スナップショット。数値は都度 GA/DB で再取得のこと）
> - Web新規: 約2,500/月（日本のOrganic Search中心、エンゲージ率0.566/滞在197秒）
> - ツールページ: 1,788ユーザー/月 → 計算23%（407人）→ 計算後CTAクリック約4%（約16）
> - デバイス: mobile 66% / desktop 31% / tablet 3%
> - 実登録(DB): 429/月（Apple 196 / Google 150 / email 83）、5月575をピークに減少
> - GA web `sign_up`: 29/月（DBと大幅乖離＝計測が壊れている）
> - 高意図クエリ「野球 個人成績 アプリ 無料」: 57→33 と減少
> - ターゲット: 中高生（モバイル前提・メール弱い・ソーシャル/フレックス志向・Apple/Googleログイン主流）

---

## 0. 結論（先に）

**直接「App Storeへ」CTAで計算検索ユーザーを登録に変えようとする限り、コンバージョンは4%前後で頭打ちになる。** 理由は3つの構造的断絶：

1. **ファネル段階の不一致**：計算検索は TOFU（情報収集）。そこにいきなり BOFU（登録・アプリDL）を求めている。段階を飛ばしている。
2. **cross-device の断絶**：Web→App Store→アプリ内登録。特にdesktop 31%は物理的に行き止まり。計測も不能。
3. **意図のミスマッチ**：来訪者は「今この数字を出したい/知りたい」。「成績を継続管理したい」ではない（まだ）。

打ち手の核心は **「小さなYESを積み重ねるコミットメント・ラダーへの作り替え」** と **「計算という行為をプロダクトの実演に転換する」** こと。加えて、前提として **計測の再建**（今のままでは何を改善しても効果が見えない）。

機会規模：Web 2,500/月を代理指標ベースで3〜5%変換できれば **75〜125登録/月**。現状の総登録429/月に対し**単月で+17〜29%、実質的な倍増余地**がある無料トラフィック。

## 1. 問題の再定義：3つのフレーム

### 素朴なフレーム（今やっていること）
「ツールページに良いCTAを置いて登録/DLさせる」→ 段階と意図を無視しており上限が低い。

### 正しいフレーム
Webのコンバージョン問題は、実は**別々の2問題が融合**している：
- (a) 意図ギャップ：計算検索者は追跡アプリを（まだ）欲しがっていない
- (b) チャネル/デバイス断絶：Web→アプリはcross-deviceの崖。UX摩擦＋計測不能

この2つを1つのCTAで同時に解こうとするから失敗する。**分けて設計する。**

### さらに上位のフレーム（戦略判断）
「Webのゴール＝アプリDL」という前提自体を疑う。取りうる立場：
- **A: Web→アプリDL**（現状）。意図に合わず摩擦最大。
- **B: Web上での価値交換＋リード獲得**（オンデバイスで完結）→ 後追いでアプリへ。計測可能・意図に合う。
- **C: Webを独自のミニプロダクト化**（匿名でも価値が貯まる→登録で永続化→アプリはアップセル）。
- **D: cross-device摩擦の低減**（deferred deep link / desktopはsend-to-phone）でAの質を上げる。

**推奨は B+C+D の合わせ技。A単独をやめる。**

## 2. トラフィックを「意図 × デバイス」で切る

| セグメント | 規模感 | 現状の受け皿 | あるべき変換 |
|---|---|---|---|
| 計算意図・モバイル | 最大（mobile66%の多く） | 計算後CTA＋常設バナー | 計算→シェア/保存→ソーシャル登録 |
| 計算意図・デスクトップ | 約550/月(31%) | App Store（**行き止まり**） | Web登録 / send-to-phone / QR |
| 情報意図（コラム読者） | 大（/column/runs 56k表示等） | 常設バナーのみ | 記事内文脈CTA＋メール/フォロー |
| アプリ探し意図 | 小・**減少中** | 弱い | 最優先で防衛（最も登録率が高い層） |

**1枚のCTAで全部を賄うのが誤り。** セグメントごとに“次の一歩”を変える。

## 3. 核心の設計原則

### 原則1：コミットメント・ラダー（段階を飛ばさない）
現状は「計算(step1)」から一気に「アプリDL＋登録(step4)」を要求している。各段が小さなYESになる階段を作る：

1. **計算する**（現状23%）
2. **成績カードを作る/シェアする**（フレックス。ソーシャル志向の中高生に刺さる。登録不要でまず体験）
3. **保存/継続する**（「この記録を残す」→軽い登録。localStorage匿名状態→登録で永続化）
4. **アプリで1試合記録する**（本命アクティベーション）

step2→3の「もう作った/貯めたものを失いたくない」心理（サンクコスト/保有効果）を使う。

### 原則2：計算＝プロダクトの実演
アプリの核心価値は「試合の数字を入れるだけで全指標を自動算出・記録」。**計算検索者は“この数字が欲しい”を自ら証明済み**。ゆえに刺さる訴求は普遍的に一つ：

> 「毎回この計算、手でやってる？ アプリなら試合の数字を入れるだけで防御率もWHIPもOPSも自動。しかも記録が残ってグラフとランキングで比較できる。」

いま出した手計算の結果を、自動版・継続版に接続する。

### 原則3：ターゲット（中高生）に最適化
- **メールナーチャは弱い**。中高生はメールを見ない。
- **強いのはソーシャル**：Apple/Googleワンタップ登録、X/LINE/Instagramへのシェア、チーム内ランキングという“競争と承認”。
- したがってリード獲得の器は「メルマガ登録」ではなく **「ソーシャルログイン」＋「フォロー/通知許可」＋（自分のデータを残す）保有動機**。
- ※シェア/バイラルは魅力的な仮説だが **実データ上ほぼ未使用（§8参照）**。中心には据えず、要検証のオプション扱いにする。

## 4. 具体的コンバージョン機構（優先度順）

### T1（即効・低コスト・今スプリント）
1. **デスクトップの行き止まり解消**（着手済み）：mobile→App Store / desktop→Web登録。31%を無駄にしない。
2. **常設CTAの文言を検索意図に接続**：「アプリで成績を記録しよう」→「防御率を毎試合“自動”計算・記録。手計算はもう不要」。ツール別（`source_tool`）に出し分け。
3. **計測の最低限の再建**（詳細は§5）：これ無しに以降の効果測定は不可能。最優先の“前提”。

### T2（価値交換・意図一致）
4. **匿名保存→登録で永続化（Web版ミニ機能）← T2本命**：計算結果を localStorage に貯め、「登録すると全端末で残る/チームで共有できる」。Figma/Notion型の“もう作ったから登録”。**他人に見せびらかす動機を必要としない保有効果**で、シェアより堅い。
5. **デスクトップ send-to-phone**：QRコード＋「スマホにリンクを送る」。desktopユーザーを意図的にアプリへ橋渡し。
6. **成績カードのシェア（降格・要検証）**：**現状ほぼ未使用（直近90日で share 合計6回、計算者の約0.5%）**。中身が「匿名の単発数字」で映えないのが原因とみられる。中心に据えない。やるなら共有対象を評価バッジ付きの映えるカードにして、小さくA/Bで需要を確認してから。既存OG生成資産（`/api/og/*-card`）は流用可能だが、投資は需要検証後。

### T3（橋渡し・ナーチャ・再来訪）
7. **deferred deep linking / install referrer**：Web→App Store→インストール後に文脈を引き継ぐ（例：計算していた指標のオンボーディングに着地）。cross-deviceのUXと計測を同時改善。
8. **ソーシャル・リターゲティング**：Meta/TikTok/YouTubeのピクセルをツールページに設置し、変換しなかった96%を追う（中高生はメールよりソーシャル）。無料の巨大母集団を資産化。
9. **高意図SEOの防衛・拡張**：減少中の「〜アプリ 無料」系クエリに専用LP/コンテンツ。最も登録率が高い層を落とさない。

### T4（複利・プロダクト主導）
10. **Web版を軽いプロダクトに育てる**：複数試合の入力・保存、簡易グラフをWebで提供→アプリは“持ち歩き/通知/チーム”のアップセルに。TOFUトラフィックを自前のプロダクト体験で温める。

## 5. 計測アーキテクチャ（すべての前提）

**現状は壊れている**：GA web `sign_up` 29 vs DB 429。cross-deviceは盲目。この状態で施策を回しても効果が判定できない。

- **(a) サーバー側で登録イベントを発火**：Rails の user 作成時に provider＋取得元付きで単一シンクへ送る。DBと一致する“真の登録”を1指標で追える。
- **(b) 取得元の保存**：signup時に `acquisition_source`（utm / landing / source_tool 等）を users に保存。ツール流入起因の登録を後から集計可能に。
- **(c) Web計測を1プロジェクトに集約**：front/ に PostHog web を導入し、pageview→CTA→（web）signup をひとつのファネルで。
- **(d) web→app のブリッジ計測**：deferred deep link / install referrer で、どのWeb流入がインストール・登録に繋がったかを近似。

計測の代理KPI（当面追うもの）：`app_store_click` / `generate_lead` を `source_tool × cta_location` で、カードシェア数、匿名保存→登録率、send-to-phone クリック。

| フェーズ | 内容 | 目的 | 目安工数 | 期待 |
|---|---|---|---|---|
| P1 | デバイス別CTA(済)＋文言接続＋計測再建(サーバー側signupイベント/取得元カラム) | 盲目状態の解消・行き止まり解消 | 小〜中 | 計測可能化＋desktop救済 |
| P2 | 成績カードのシェア主役化＋匿名保存→登録 | 意図一致の価値交換・バイラル | 中 | CTAクリック率とシェア数の底上げ |
| P3 | deferred deep link＋desktop send-to-phone＋ソーシャルRT | cross-device橋渡し・再来訪 | 中〜大 | web→app転換の実効率up |

## 7. KPIツリー（測れるものだけを目標化）

- 北極星（真実）：**取得元別・実登録数/月（DB, サーバー側計測）**
- 代理（Web内）：ツール訪問 → 計算率(23%) → CTAクリック率(≈4%) → （web）signup率
- ラダー指標：カード作成率 / シェア率 / 匿名保存率 / 保存→登録率 / send-to-phoneクリック率
- 防衛指標：高意図クエリ（「〜アプリ」）のクリック数・順位

「計算→登録率○%」はcross-deviceで直接測れないため**目標化しない**。代理指標を上げ、サーバー側の取得元別登録で答え合わせする。

## 8. 非直感的な論点・リスク（あえて疑う）

- **そもそもこの流入は変換すべきか？** → Yes。無料かつ大規模。ただし“直接DL”ではなく“意図一致の価値交換”で。低意図だからと捨てるのは誤り（1%改善でも月25登録）。
- **メールを取りに行くべきか？** → 中高生には弱い。**ソーシャルログイン＋シェア＋通知許可**を優先。メールは保護者/大学生セグメント向けの副次。
- **CTAを増やしすぎるリスク**：既に上部SmartAppBanner＋下部固定ナビ＋常設バナー×2。固定要素の追加は逆効果。**数ではなく“文脈と段階の一致”で効かせる。**
- **シェアはデータ上ほぼ未使用**：直近90日で `share` 合計6回（era_result 3 / batting_average_result 2 / stats_card 1）。計算者（月407人）の約0.5%しかシェアしていない＝ボタンを見た人すら押さない。原因は共有対象が「匿名の単発数字」で映えないこと。**バイラルは未検証の仮説であり、戦略の中心に置かない。** やるなら“評価バッジ付きの映えるカード”に作り替えてから小さくA/Bで需要を確認する。
- **計測再建をスキップする誘惑**：最も地味だが最重要。ここを飛ばすと以降すべてが体感頼みになる。

## 9. 次アクションの推奨

1. **P1の計測再建を最優先で着手**（Railsサーバー側 signup イベント＋`acquisition_source` カラム）。これで初めて「Web起因の登録」が見える。
2. 並行して**常設CTAの文言を意図接続＋デバイス別**に（低コスト・PR #380の延長）。
3. その上で**P2（成績カードのシェア主役化＋匿名保存→登録）**をプロトタイプし、カード作成率/シェア率で検証。

「めちゃくちゃ深く」の結論：**勝ち筋は“計算という実演の直後に、保有（匿名保存→登録で永続化）でソーシャルな小さなYESを積ませ、ソーシャルログインで刈り取り、サーバー側計測で答え合わせする”こと。**（シェア/バイラルは実データ上ほぼ未使用のため中心に据えず、要検証オプションへ降格。）App Store直行CTAの最適化は、この土台の上で初めて意味を持つ。
