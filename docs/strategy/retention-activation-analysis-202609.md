# リテンション / アクティベーション分析（2026-09-26 時点スナップショット）

App Store Connect のベンチマークで「28日目リテンションがピア中央値の半分以下」と出たことを起点に、
PostHog の実データで離脱の正体を特定した記録。

> 注意: 本ドキュメントの ASC / PostHog の数値は 2026-09-26 取得時点のスナップショット。
> 最新値は都度 ASC / MCP で取り直すこと。
> PostHog のコホートは「初回イベント発生日」基準。プロジェクト作成が 2026-06-20 のため、
> 6/28 より前を初回とみなせるユーザーは存在せず、コホート開始を 6/28 に置いている。

## 結論

**D7→D28 の離脱の正体は「一度も試合を記録しないまま終わるユーザーが新規の 55.6% いる」こと。**
1試合でも記録すれば 21日後の定着率は 19.8% → 63.1%（3.2倍）に跳ね上がる。

- プロダクトの価値自体に問題はない。記録した人は定着している（11試合以上で 93.1%）。
- 問題は**初回アクティベーション**。記録フォームまでは来ているのに完了していない人が新規の 33%。
- ASC の「D28 = 2.80%」はこのアプリが**週1利用**であることによる構造的な低さで、
  ピア比較（毎日開くスコア速報系を含む）は不利に歪んでいる。週次で見ると W4 以降フラット化する健全な形。

## 1. 試合記録数と21日後定着率

対象: 2026-06-28 〜 08-22 に初回起動した新規 1,386人（21日以上観測済み）
定着の定義: 初回イベントから 21日以上あとにもイベントがある

| 記録した試合数 | ユーザー数 | 構成比 | 21日後も利用 |
| --- | --- | --- | --- |
| **0試合** | **771** | **55.6%** | **19.8%** |
| 1試合 | 168 | 12.1% | 63.1% |
| 2〜3試合 | 139 | 10.0% | 76.3% |
| 4〜10試合 | 192 | 13.9% | 80.7% |
| 11試合以上 | 116 | 8.4% | 93.1% |
| 全体 | 1,386 | 100% | 45.3% |

0試合 → 1試合の段差（19.8% → 63.1%）がプロダクト全体で最大のレバー。

## 3. 週次リテンション曲線

PostHog / `$screen` の初回発生コホート、直近90日、加重平均。

| | W1 | W2 | W3 | W4 | W8 |
| --- | --- | --- | --- | --- | --- |
| 週次リテンション | 約36% | 約30% | 約26% | 約24% | 約20〜24% |

W4 以降フラット化しており、下げ止まっている。「落ち続けている」形ではない。

### ASC の D28 が低く出る理由

直近60日、アクティブだった週における利用日数の分布:

| 週あたり利用日数 | user-week 数 | 構成比 |
| --- | --- | --- |
| 1日 | 2,732 | 54.6% |
| 2日 | 1,089 | 21.8% |
| 3日 | 596 | 11.9% |
| 4日 | 303 | 6.1% |
| 5日以上 | 286 | 5.7% |

平均 1.9日/週、**アクティブな週の 54.6% は「週1日だけ」**。
ASC の日次リテンションは「28日目ちょうどに起動していたか」を測るため、
週1利用のアプリでは週次リテンションの 1/4 程度に圧縮されて表示される。

ASC ベンチマークのピアセット「スポーツアプリ」には毎日開くスコア速報・ニュース系が多く含まれるため、
**D1/D7/D28 の比較はこのアプリに構造的に不利**。ASC 側で見るなら CVR とベンチマークの推移、
定着の実態は PostHog の週次で見る、という使い分けにする。

## 5. 計測の穴（分析中に判明）

数値を正しく読むために直すべき箇所。

1. **`app/(game-record)/plate-appearances` に `trackGameRecordStepViewed` が無い。**
   打者フローは step1 から直接この画面へ遷移する（`step1-game-info.tsx` の分岐）ため、
   **打者の最大の入力画面が計測対象外**。457人の離脱地点を特定するにはここの計測が必須。
2. 編集モードでは `trackGameRecordCompleted` を意図的に送らない設計（`summary.tsx` の `handleComplete`）。
   summary 閲覧ユーザー数（1,196）と完了ユーザー数（918）の差を離脱と読むと誤る。
3. `step2-batting` は pattern 未確定時のみ通る旧フロー。`step=2` が 67人しかいないのは仕様であってバグではない。

## 6. 打ち手（優先順）

| # | 施策 | 根拠 |
| --- | --- | --- |
| 1 | `plate-appearances` 画面に step 計測を追加 | 457人の離脱地点が現状まったく見えない |
| 2 | 初回記録の完了までオンボーディングで伴走する | 0→1試合で定着 3.2倍。最大のレバー |
| 3 | フォロー・グループへの導線を初回体験に組み込む | 週1利用を増やす仕掛けが死んでいる |
| 4 | 試合翌日の再訪導線（プッシュ等） | 週1利用前提の設計に合わせる。誤送信事故を踏まえ慎重に設計する |

#2 の具体的な中身（どの入力項目で詰まるのか、項目数が多いのか、スコア入力が難しいのか）は
現在のデータでは特定できない。推測で UI を変える前に #1 で離脱地点を確定させる。
