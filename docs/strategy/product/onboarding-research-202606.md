# BUZZ BASE オンボーディング改修方針（モバイル中心 / 2026年6月）

関連 Issue: ippei-shimizu/buzzbase#375
作成日: 2026-06-14
対象: BUZZ BASE モバイルアプリ（Expo / React Native）
データソース: `data/db-snapshots/202606-user-acquisition/` の本番DB真値

## 1. 課題の前提（真値ベース）

| 指標 | 値 | 評価 |
|------|-----|------|
| 月間新規登録（DB） | 513 | 健全 |
| 真の登録CVR（GA4 新規UU 2,227 比） | 23.0% | 健全 |
| メール確認率 | 93.18% | 健全 |
| SSO 比率 | 80% (Apple 50.1% + Google 29.8%) | 既に主流 |
| **登録後 ever 試合記録率** | **61.1%（過去2ヶ月 956人中 584人）** | **39%が記録ゼロ離脱** |
| 登録後 7日以内記録率 | 57.9% | ほぼ初日で確定 |
| **グループ所属率** | **7.25%（1,670中121人）** | **ネットワーク効果未達** |
| 1人グループ数 | 126個 | 招待が機能していない |

最大のボトルネックは「**登録 → 初回試合記録への離脱 39%**」と「**グループ未参加 92.75%**」の2点。GA4 ベースで疑った登録 CVR は実は健全であり、戦略の焦点は完全に「登録後の体験」と「ネットワーク効果」へ移る。

## 2. 現状の登録フロー全体像

### 2-1. メール登録経路（メイン）

```
1. /(auth)/sign-up         メール / パスワード入力
       ↓ signUp() 成功
2. /(auth)/confirmation-pending   メール確認待ち画面
       ↓ ユーザーがメール内リンクをタップ
3. ディープリンク confirmation-success を _layout.tsx が受信
       ↓ Alert「メール認証完了」→「OK」
4. /(auth)/sign-in          サインイン画面（自動ログインしない）
       ↓ ユーザーが手動でメール/パスワードを再入力
5. /(tabs)/index            ダッシュボード（HomeScreen）
```

### 2-2. Google / Apple SSO 登録経路

```
1. /sign-up or /sign-in で SSO ボタン
       ↓ googleLogin() / appleLogin()
2a. requires_username: true → /(auth)/username-registration
       ↓ user_id（半角英数+_、3文字以上）入力
3a. /(tabs)/index           ダッシュボード
       または
2b. requires_username: false → 直接 /(tabs)/index
```

### 2-3. 直後に表示されるダッシュボード（新規ユーザー視点）

`HomeScreen` → `DashboardContent` の構成（全部 Empty State だらけ）:

```
[ヘッダー: 通知ベル + メニュー]
[「試合結果を記録する」ボタン（headerComponent）]   ← 唯一の明示的CTA
[StatsOverview]
  [打撃成績]
    [フィルタバー（年度/種別/シーズン）]            ← 新規には完全にノイズ
    [EmptyState「打撃データがありません」]          ← 行動誘導なし
  [投手成績]
    [フィルタバー]
    [EmptyState「投手データがありません」]          ← 同上
[RecentGameResults]
  [EmptyState「試合結果がありません」]              ← 同上
[GroupRankings]
  [EmptyState「グループに所属していません」]
  [「グループを作成」ボタン]                        ← ここだけCTA付き
```

## 3. 構造的問題（重大度順）

### 問題A: ダッシュボードが新規ユーザーに「死亡画面」として表示される【最重大】

`components/dashboard/EmptyState.tsx` は `title` と `subtitle` のみを淡色で表示する純粋な「データなし」表示で、行動誘導が一切ない。新規ユーザーは:

- 「打撃データがありません」
- 「投手データがありません」
- 「試合結果がありません」
- 「グループに所属していません」

という殺風景な Empty State を縦に3〜4個並べて見ることになる。ここで「何をすべきか」「アプリの価値は何か」が全く伝わらない。

唯一意味のあるCTAは `headerComponent` の「試合結果を記録する」ボタンだが、これを押した先の体験（試合情報入力 → 球場 → 対戦相手 → スコア…）が重く、初回利用には負担が大きすぎる可能性。

### 問題B: メール登録経路は「2段階ログイン」になる

`_layout.tsx` の `handleDeepLink` を見ると、メール認証成功後にユーザーへ表示されるのは:

```
Alert「メール認証完了」「メールアドレスの認証が完了しました。ログインしてください。」
       ↓ OK
sign-in.tsx へ replace
```

つまり、ユーザーは:

1. メアド + PW 入力（sign-up）
2. メアドアプリへ遷移 → 確認リンクタップ
3. アプリに戻る → Alert
4. もう一度メアド + PW を**手動入力**（sign-in）

という4段階の操作を要求される。メール確認率 93.18% は通過しているので、この後の「手動ログイン → 初回試合記録」のどこかで離脱している可能性が高い。

### 問題C: メール登録は username（user_id）登録ステップを通らない

`sign-up.tsx` のメール登録経路は確認メール待ちに遷移するだけで、`username-registration.tsx` を経由しない。一方 SSO は `requires_username` で強制経由する。

結果、メール登録ユーザーは `user_id` 未設定でダッシュボードに到達する可能性がある。プロフィール画面（`/(profile)/[userId].tsx`）やグループ機能で識別子として使われるため、後で不整合が発生するリスクがある。

### 問題D: グループ機能への誘導がダッシュボードに薄い

グループタブ（`(tabs)/(groups)/index.tsx`）には「友達とグループを作成しよう！」バナーと「招待コードでグループに参加」ボタンが揃っているが、ダッシュボード初期表示の `GroupRankings` セクションには「グループを作成」ボタンしかない（招待コード参加への導線なし）。

新規ユーザーは「自分で作る」か「グループタブに能動的に移動して招待コードを使う」かしか選択肢がなく、グループ所属率 7.25% / 1人グループ 126個という現状の数字を生んでいる。

## 5. 改善案（優先順位順）

### Quick Win（Month 1 / 工数 S-M）

#### 改善1: アプリ初回起動時のオンボーディング画面（3ステップ）【最優先 / 工数M】

アプリダウンロード後、サインアップ画面を表示する前に **3 ステップのオンボーディング画面**を挿入する。BUZZ BASE が何を提供するかを未登録ユーザーに直感的に伝え、登録動機を上乗せする。競合のヒットメーカー（45,000DL）・GameChanger・Strava はいずれも同様の初回オンボーディングを持つ業界標準UX。

##### 表示タイミングと制御

- **初回起動時のみ表示**。`AsyncStorage` の `onboarding_completed: true` フラグで2回目以降スキップ
- 配置: 新規ルート `/(onboarding)/welcome.tsx` を作成し、`app/_layout.tsx` でディスパッチ
- 認証チェック前に振り分ける（既ログインの場合はオンボーディング後 `/(tabs)` へ）

##### 設計

```
Step1: 「打席を入力するだけで自動計算」
  → 打率・OPS・防御率・29指標を自動で算出するイラスト
  → コピー「もう自分で電卓を叩かなくていい」

Step2: 「チームメイトとランキングで競う」
  → グループランキングのスクリーンショット風イメージ
  → コピー「友達と打率を競い合おう」

Step3: 「成長を1枚のグラフで」
  → 成績推移グラフのサンプル
  → [はじめる] ボタン → /(auth)/sign-up へ
```

##### 必須UI要件

- ページインジケーター（●○○ → ○●○ → ○○●）
- 左右スワイプで前後移動
- **右上に「スキップ」ボタン常設** → sign-up へ直行
- 戻る矢印（Step2 以降）

##### 重要な制約

- **3ステップを超えない**（5以上は離脱増、業界平均は3）
- **スキップ可能を必ず常設**（登録障壁にしない）。真値CVR 23% は健全なのでこれを壊さない設計
- **A/B テストで効果検証**（オンボーディング表示あり/なしで sign_up CVR を比較。実装は Phase 2）
- 既存ユーザーのアプリ再インストール時にも表示される（フラグはデバイス側保存）。これは仕様として割り切る

##### 期待効果

- アプリの世界観を初接触で伝え、特にメール登録経路の「2段階ログイン後に殺風景なダッシュボード」問題を最小化
- 中高生ターゲットの「アプリを一瞬で理解する」文化との親和性
- 競合（特に中高生に弱いPLAY by TeamHub の代替）として価値訴求の第一印象を強化

#### 改善2: DashboardのEmptyStateに行動誘導CTAを追加【工数S】

現状の `components/dashboard/EmptyState.tsx` は文言だけ。これを「文言 + CTAボタン」を取れるよう拡張する:

```tsx
interface EmptyStateProps {
  title: string;
  subtitle?: string;
  action?: { label: string; onPress: () => void };
}
```

各 Empty に対応する CTA:
- 打撃データ Empty → 「初めての試合を記録する」 → step1-game-info
- 投手データ Empty → 「初めての投球を記録する」 → step1-game-info（投手モード）
- 試合結果 Empty → 「初めての試合を記録する」 → step1-game-info
- グループ Empty → 「グループを作成」（既存）に加えて「招待コードで参加」を追加

期待効果: 試合記録ゼロ層 39% → 30% に圧縮（仮説）

#### 改善3: 新規ユーザー判定で「ウェルカムカード」を最上部に表示【工数M】

改善1 が「登録**前**の価値訴求」なのに対し、これは「登録**後**のダッシュボード初回表示で次の行動を提示する」という別物として並存させる。

`data.recent_game_results.length === 0` && `data.batting_stats.aggregate` 不在 = 新規ユーザーと判定。`DashboardContent` の最上部（headerComponent の直後）に以下のカードを表示する:

```
┌─────────────────────────────────────────┐
│ BUZZ BASEへようこそ                       │
│                                          │
│ 3ステップで始めよう                       │
│  ① 最初の試合を記録する                  │
│  ② 自動で打率・OPS・防御率が計算される    │
│  ③ チームメイトを招待してランキングを開始 │
│                                          │
│  [試合を記録する] [友達を招待する]        │
└─────────────────────────────────────────┘
```

「友達を招待する」は username 未設定の場合は username-registration に飛ばす、設定済みなら直接 /(groups)/create か /(groups)/share-invite へ。

#### 改善4: フィルタバーを試合データがある時のみ表示【工数S】

`StatsOverview` の `BattingSection` / `PitchingSection` で `!agg || !calc` の時にフィルタバー（`buildFilterBar`）の描画もスキップする。現状は Empty 表示でもフィルタが残るため新規ユーザーに無用な認知負荷を与えている。

#### 改善5: GroupRankings の Empty に「招待コードで参加」ボタン追加【工数S】

`GroupRankings.tsx` の Empty 表示部分に、既存の「グループを作成」に加えて「招待コードで参加」ボタンを追加。`/(groups)/join` に遷移させる。新規ユーザーがチームメイト主導で参加するパターンを救済する。

#### 改善6: メール登録経路でも自動ログイン → username-registration を経由【工数M】

`confirmation-pending` でメール確認完了を検知したら（バックエンド側でポーリング or WebSocket）、自動的に sign-in を実行して、`/(auth)/username-registration` に遷移する。フローを SSO と統一する。

代替案として「sign-up 時点で username 入力もまとめて行う」も検討する（フィールド数増えるが2段階ログインが解消される）。

### 中期改善（Month 1-2 / 工数 M-L）

#### 改善7: 初回試合記録のミニマム版を提供【工数L】

step1-game-info で要求される必須項目を最小化（球場・大会名は任意、試合種別はデフォルト「練習試合」）。練習や打席なしの試合でも気軽に1試合記録できるようにする。BUZZ BASE のコアバリューは「自動計算」と「ランキング共有」なので、最初は1打席だけでも記録できればよい。

#### 改善8: 登録後 1日 / 3日 / 7日後のリエンゲージメント通知【工数M】

「最初の試合をまだ記録していませんね」というプッシュ通知またはメール。`first_visit` から N 日経過 + `match_results` レコードなしのユーザーに対して送信。

**注意**: 過去のローカル Rails から本番ユーザーへの push 通知誤爆事故（[[project_push_notification_local_leak_incident]] 参照）を踏まえ、本番環境分離のチェックリスト厳守。

### 長期改善（Month 2-3）

#### 改善9: グループ招待UXの抜本改善（Issue #377）
本ドキュメントでは詳細扱わない。OGP画像生成・ワンタップシェア（LINE/X）の実装で別途進める。

#### 改善10: サンプルデータ機能【工数L】
「サンプルデータを見る」ボタンで、現状の Empty 画面が試合10件入った状態でどう見えるかをプレビュー。価値訴求のため。なお、改善1 のオンボーディング画面の Step2/Step3 にスクリーンショット風サンプルを含めることで、登録前にこの体験を一部前倒しできる。
