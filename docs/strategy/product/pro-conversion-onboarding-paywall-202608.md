# BUZZ BASE Pro 加入率向上のための Paywall / オンボーディング改修設計（2026年8月）

作成日: 2026-08-27
対象: BUZZ BASE モバイルアプリ（Expo / React Native）
関連: `onboarding-research-202606.md`（獲得・活性化の改修）/ `pro-plan-prd-202605.md`（Pro の機能・価格）
外部参考: Superwall「Multi-page onboarding paywalls convert 37% better than single-page」（2026年2〜5月、オンボーディング配置のペイウォール表示4,000万件超の分析。1画面型 9.07% に対しマルチページ型 12.41%）

## 1. 狙い

Pro 加入率（トライアル開始率）を上げる。課金はまだ本番リリース前のため、リリース前に計測と導線を作り切り、リリース直後から改善サイクルを回せる状態にする。

## 2. 現状

### 2-1. オンボーディングに Pro 訴求が無い

`app/(onboarding)/welcome.tsx` は `constants/onboarding.ts` の3スライド（自動計算 / ランキング / 成長グラフ）を横スクロールで見せ、「はじめる」でサインアップへ送るだけ。Pro には一切触れていない。

参考記事が扱う「オンボーディング配置のペイウォール」自体が存在しないため、記事の知見（1画面 → 複数画面）は、そのままでは適用先が無い。

2026-09-26 追記: Phase 1 の配置を登録直後へ変更したことでこの前提は解消される。ただし訴求を足すのは登録**後**のシーケンスであり、この `welcome.tsx`（登録前・未ログイン）には Pro 訴求を入れない。理由は 7 節のリスク表と 8 節の決定事項を参照。

### 2-2. Paywall は典型的な1画面完結型

`components/pro/PaywallModal.tsx`（1252行）が、1つの縦スクロールに以下を積んでいる。

1. ハイライトカード（トリガーになった機能の訴求）
2. 「PRO でできること」= 全31機能のグループ別比較表（`FEATURE_GROUPS`）
3. プラン選択（月額 / 年額）
4. CTA・復元・規約リンク

参考記事が「1画面型の敗因」として挙げる「価値の説明・不安の解消・価格の提示・支払いの要求を同時に1画面へ詰め込む」構造そのもの。特に31項目の比較表は縦に長く、価格に到達する前にスクロール疲れを起こしている可能性がある。

表示タイミングは機能ゲート到達時のみ（成績分析 / 目標 / 素振り / グループ参加 / ノート / 振り返り）。`app/pro/index.tsx` へは設定画面と特商法ページからのみ遷移できる。

### 2-3. Paywall のファネルを計測できていない

PostHog は導入済み（`posthog-react-native`）だが、`utils/analytics.ts` にある Pro 関連イベントは `trackProFeatureTapped` のみ。Paywall の表示・プラン選択・購入開始 / 完了・離脱のイベントが無く、参考記事が定義するような CVR（表示ユーザーのうちトライアル開始または購入した割合）を算出できない。

改修の前に、ここを埋める必要がある。

### 2-4. 初回記録直後は既に割り込みが混雑している

`app/(game-record)/summary.tsx` の `handleComplete` は、記録保存後に次の順で処理する。

1. ストアレビュー促進プロンプト（`tryShowPrePrompt("complete")`）。出た場合はここで終了
2. インタースティシャル広告（`showMatchSaveInterstitial`。`no_ads` エンタイトルメント保持者はスキップ）
3. 試合結果一覧へ遷移

ただしレビュー促進は `hooks/useStoreReview.ts:19` の `MIN_DAYS_SINCE_INSTALL = 7` により、インストールから7日未満は発火しない。初回記録はほぼ初日に発生する（7日以内記録率 57.9%、ほぼ初日で確定）ため、**初回記録直後にレビュープロンプトが競合する可能性は低い**。実質の競合はインタースティシャル広告のみ。

### 2-5. リリース後の実測（2026-09-24 追記）

Phase 0 の計測は mobile 2.0.3（2026-09-13 配信）から稼働している。以降12日間の PostHog と本番 DB を突き合わせた結果は次のとおり。

| 段階 | ユニークユーザー |
| ---- | ---- |
| アプリのアクティブユーザー（2026-08-14 以降） | 1,450 |
| Pro 機能のロック表示をタップ | 138 |
| Paywall 表示（2.0.3 以降の12日間） | 80 |
| 購入ボタン押下 | 2 |
| 購入完了 | 1 |

読み取れたこと:

- **漏れの最大点は Paywall の中**。表示から購入ボタンまで 2.5% しか進まない
- **比較表の大半が閲覧者に無関係**。Pro 32機能のうち20件以上が練習・目標・ノート系だが、その利用者は全ユーザー3,581人のうち練習記録45人 / 目標25人 / ノート84人にとどまる。無料上限到達（`free limit reached`）も6週間で7人しか発生していない
- **成績分析は本人データで即価値を出せる**。打球方向データ保有1,282人、カウント別573人、球種別544人
- **シーズン跨ぎ推移が Paywall 表示の約7割を占めるが、複数シーズンの記録を持つのは95人**。大半の閲覧者には空のグラフしか見せられていない
- **トライアル3件はいずれも初日に打席記録を大量入力して成績画面を見た層**。うち2件が37時間・5日で解約しており、「見たいものを見終わったら終わり」という動きが出ている

## 3. 制約と前提

- **ターゲットは中高生**。自分の決済手段を持たない層が一定いるため、KPI は「購入」ではなく「トライアル開始」を主指標に置く
- **登録後 ever 試合記録率は 61.1%**（`onboarding-research-202606.md` の本番DB真値。過去2ヶ月 956人中 584人）。「初回記録後」に Paywall を置くと、リーチできるのは登録者の約6割にとどまる。この制約を承知のうえで、価値を体験した層に絞って訴求する判断とする
- **記録アプリは初回起動時点では価値が実感されない**。1試合も記録していない状態での課金訴求はジャンル的に不利。参考記事の「支払いを求める前に価値を確立する」を、この文脈では「アプリ内の説明」ではなく「実際に1試合記録して自動計算を体験させること」で満たす
- **iOS 審査**: 自動表示する Paywall には常に閉じる導線が必要。既存 `PaywallModal` は閉じるボタンを持つのでこれを踏襲する
- **`pro_features` フラグ**: OFF の間は購入導線（プラン一覧・加入・復元）が出ない設計（`PaywallModal.tsx:481-524`）。計測とオンボ改修は課金リリース前に先行して入れられる

## 4. KPI 定義

分母・分子を固定する。参考記事の定義に揃える。

| 指標 | 定義 |
| ---- | ---- |
| Paywall CVR（主指標） | `paywall_viewed` したユニークユーザーのうち、`paywall_purchase_completed`（トライアル開始を含む）に至った割合。配置（placement）別に算出 |
| ステップ通過率 | マルチページ Paywall の各ステップの `paywall_step_viewed` ユニークユーザー数の推移 |
| 初回記録到達率 | 登録ユーザーのうち初回試合記録を完了した割合（既存の課題指標。Paywall のリーチ上限を規定する） |
| トライアル → 有料転換率 | トライアル開始者のうち初回課金に至った割合。back の `subscription` ステータス遷移から算出 |

表示回数が極端に少ない配置・バリアントは判断材料から外す。

## 5. 施策

### Phase 0: ファネル計測の整備（実装済み / mobile 2.0.3・2026-09-13 配信）

`utils/analytics.ts` に以下を追加する。既存の命名（`posthog?.capture("...")`）に合わせる。

実装時にイベント名は object-verb（スペース区切り）へ揃えたため、実際に飛んでいるのは
`paywall viewed` / `paywall step viewed` / `paywall plan selected` / `paywall dismissed` /
`upgrade started` / `purchase completed` / `purchase failed` / `free limit reached` になる。
`placement` は導線ごとの機能キーを表す `trigger` に統合した。

| イベント | プロパティ |
| ---- | ---- |
| `onboarding_step_viewed` | `step_index`, `illustration` |
| `onboarding_completed` | `skipped`（スキップ経由か） |
| `paywall_viewed` | `placement`, `trigger_feature`, `variant` |
| `paywall_step_viewed` | `placement`, `step_index` |
| `paywall_plan_selected` | `plan_type`, `placement` |
| `paywall_purchase_started` | `plan_type`, `placement`, `is_trial_eligible` |
| `paywall_purchase_completed` | `plan_type`, `placement`, `is_trial` |
| `paywall_dismissed` | `placement`, `step_index`（どのステップで閉じたか） |
| `paywall_restore_tapped` | `placement` |

`placement` の値は `feature_gate` / `first_record` / `settings` / `onboarding` を想定し、定数として一元管理する。

購入完了イベントは `PaywallModal` と `app/pro/index.tsx` の両方の購入処理に入れる（同じロジックが二重にあるため、共通フックへの切り出しを合わせて検討する）。

### Phase 1: 登録直後のオンボーディングシーケンスに Paywall を組み込む（2026-09-26 方針変更）

当初案は「初回記録完了直後」だったが、配置を **登録直後（ユーザー名登録の直後）** へ変更する。初回記録直後の Paywall は実装しない。

#### 変更理由

- **リーチが桁で違う**。初回記録直後はリーチが登録者の約48%（90日コホートで登録1,337人中、記録完了643人）に制限される。登録直後なら登録者のほぼ全員に届く。現状の Paywall 到達は新規1,792人中17人（0.9%）しかなく、まず母数を作る段階にある
- **参考記事が扱っているのはまさにこの配置**。記事のマルチページ型 CVR 12.41% は「オンボーディング配置のペイウォール」の数字であり、機能ゲート経由の数字ではない。2-1 節で「適用先が無い」としていた前提が、この変更で解消される
- **記事が挙げる「セットアップ文脈では追加画面が摩擦ではなく自然な流れとして認識される」が、ここでだけ成立する**。ユーザー名登録という必須フォームの直後なので、画面が続くこと自体が不自然でない

#### 制約: 登録前（未ログイン）には置けない

`back/app/services/revenue_cat/user_resolver.rb` は `app_user_id` を `Subscription#revenuecat_user_id` または `User.id` でしか解決しない。RevenueCat の匿名 ID（`$RCAnonymousID:...`）はどちらにも当たらず `UnresolvedUserError` になるため、**未ログインで購入されると課金は成立するのに back 側で entitlement が付与されない**。`loginRevenueCat` が呼ばれるのはログイン成功時（`authService` / `googleAuthService` / `appleAuthService`）だけである。

したがって mobile の既存オンボーディング（`app/(onboarding)/welcome.tsx`。sign-up より手前で未ログイン）には置けない。置ける場所は登録直後のみ。

#### 構成

`onboarding-research-202606.md` の改善3（登録後プロフィール入力）と地続きの1本のシーケンスとして設計する。

| 順 | 画面 | 役割 | スキップ |
| ---- | ---- | ---- | ---- |
| 1 | `username-registration` | 必須項目（ユーザー名 / ユーザーID） | 不可 |
| 2 | `profile-setup` | チーム / ポジション / 利き腕 / 打席。記事の「Design your trial」に相当し、次画面の訴求をパーソナライズする前提になる | 可 |
| 3 | `value` | ポジションに合わせた分析の紹介。既存 `PaywallSlides` を流用 | 可 |
| 4 | `plan` | 月額 / 年額、トライアル、CTA、復元、規約 | 可 |
| 5 | ダッシュボード | - | - |

**パーソナライズはスライド順で表現する。** `PaywallSlides` の `orderSlides` が `trigger` で先頭スライドを差し替える仕組みを既に持つので、profile-setup の回答から擬似トリガーを決めて渡す。投手なら球種別・コース別、打者なら方向別・カウント別を先頭にする。プロフィールをスキップした場合は既定順。

Phase 2 で作った `PaywallFlow` / `usePaywallPurchase` / `usePaywallSteps` をそのまま使い、購入処理は新規に書かない。

各画面に閉じる導線を置き、`paywall dismissed` の `step` でどこで落ちたかを測る（iOS 審査の要件でもある）。

#### 初回記録直後には出さない

初回記録直後にも出すと初日に2回 Paywall を見せることになるため、一本化する。`app/(game-record)/summary.tsx` の割り込みは現状どおり「ストアレビュー促進 → インタースティシャル広告」のままとし、Paywall は追加しない。

広告非表示（`no_ads`）はこの配置では訴求に含めてよい。初回記録直後と違って、閉じた直後にインタースティシャル広告が出る順序にならないため。

### Phase 2: 既存 PaywallModal を「価値画面 + プラン画面」に分割（2026-09 実施 / ippei-shimizu/buzzbase#590）

リリース後の実データを見て、当初案（3ステップ）から2ステップへ簡素化した。根拠は 2-5 節を参照。

参考にしたのは mixi「みてね」のプレミアム加入導線で、構造は次の3層に分かれている。

1. 入口画面: トリガーになった機能だけを大見出し1行 + ビジュアル1枚で見せる。価格も比較表も出さない。CTA は画面下に常時固定
2. スクロール領域: 機能ごとに「ビジュアル + 見出し + 1〜2文」を1ブロックとして並べ、比較表は最後、全機能一覧は別画面のアコーディオンへ逃がす。契約条件・FAQ・復元・規約で終わる
3. プラン選択画面（CTA 押下後）: 月額と年額を横並びにして月あたり換算を併記し、CTA は「このプランで続ける」

BUZZ BASE ではプランが1種類2周期のためプラン切替タブは作らず、みてねの撮り下ろし写真にあたる部分を「本人の成績データ」に置き換える。

表示形式は**全画面**とする。従来のシート型（高さ 88%）は画面下部が常に背景へ取られ、図を大きく見せられないため。閉じる導線はヘッダー右上に固定し、プラン画面では左に戻るボタンを置く。

| ステップ | 内容 |
| ---- | ---- |
| value（価値画面） | 「BUZZ BASE PRO」の見出し、機能紹介のスライドショー、トリガー機能の見出しと説明、同系統の機能ブロック最大3件、全機能一覧のアコーディオン、FAQ 4項目 |
| plan（プラン画面） | 月額 / 年額の横並び（年額は月あたり換算とお得額を併記）、復元、契約条件、規約リンク |

決定事項:

- **見出しの直下にスライドショーを置く。** Pro でできることを 1 枚ずつ横スクロールで見せる。トリガーに対応するスライドを先頭へ並べ替え、自動送りはユーザーがスワイプした時点で止める
  - **図はすべて作り物のイラストにし、本人の成績も実際の分析カードも描かない。** Paywall で本物の分析を出すと未加入のまま中身が見えてしまい、ゲートの意味が無くなる
  - 7 枚（方向別 / コース別 / 対戦投手別 / 球種別 / カウント別 / シーズン推移 / 広告非表示）を `PaywallSlideArt` に SVG で描く
  - **構図はスライドごとに変える。** カード・端末・円形吹き出しといった部品は共有し、配置と主役だけを入れ替える。全 5 枚を同じ「端末モック中央」で作ると、横に送っても違いが伝わらない

| スライド | 構図 |
| ---- | ---- |
| 方向別の打率 | 端末の画面に球場図を映し、左右に円形の吹き出しを重ねる |
| コース別の打率 | 端末の画面に 5x5 のヒートマップを映し、下にホームベースを置く |
| 対戦投手別の打撃成績 | 端末の画面に投手の一覧を映し、左に得意な投手のカードを飛び出させる |
| 球種別の打率 | 端末を使わず、球種ごとのボールを 2x2 に並べて打率を添える |
| カウント別の打率 | 端末そのものを 3 台、扇状に並べて中央を前に出す |
| シーズン推移 | 左で見切れる端末と、右から浮かぶグラフカード |
| 広告非表示 | 端末の広告枠に大きな禁止記号を重ねる |

成績分析のスライドは打率のダミー値を図に載せ、色分けは実際のカードと同じ固定閾値のスケールに揃える。端末を映す図は共通の `PhoneMock`（ベゼル・ダイナミックアイランド・サイドボタン・ホームインジケータ・画面クリップ）を使う。

  - 撮り下ろし画像は用意しない。素材が無く、機能の輪郭を示す簡略図のほうが「何ができるか」が伝わる
  - 図の高さは 190pt に固定する。実カードをそのまま貼るとスライド 1 枚が画面を超える
- **比較表は価格の手前に置かない。** `FEATURE_GROUPS` の32行は既定で畳み、「Pro の全機能を見る」から開く
- **訴求項目はトリガーと同系統に絞る。** 成績分析 / 練習・ノート / 目標・課題 / 素振り の4系統を定義し、トリガーが属する系統から最大3件を出す。どの系統にも属さないトリガーは成績分析2件 + 広告非表示にフォールバックする
- **シーズン跨ぎ推移はトリガー時に分岐する。** 記録が1シーズン分しかないユーザーには空のグラフしか作れないため、「来シーズンから比較できる」案内に差し替え、図と機能ブロックを方向別の打率に置き換える
- **FAQ で「解約しても記録は消えない」ことを明示する。** 分析表示だけがロックされ、再加入すればすぐ戻ることを書く。トライアル解約者が初日に見終えて離脱する動きへの対策
- **プラン画面では年額に月あたり換算を併記する。** 端数は切り上げ、実際より安く見せない

実装は `mobile/components/pro/paywall/` に分離し、モーダル（`PaywallModal`）と全画面（`app/pro`）が同じ `PaywallFlow` / `usePaywallPurchase` / `usePaywallSteps` を共有する。これにより両者で訴求と課金処理が分岐しない。

現行の1画面型はバリアントとして残さない。実データ上、1画面型のプラン到達率が低すぎて比較の母数を確保できないため、2画面型へ切り替えたうえで Phase 3 の A/B は別軸（プラン初期選択など）で行う。

### Phase 3: A/B テストと最適化

PostHog の feature flag でバリアントを出し分ける。

- 比較軸1: 1画面型 vs マルチステップ型（参考記事の主張の自社検証）
- 比較軸2: 登録直後の Paywall あり / なし（登録 → 記録フロー開始率への副作用を同時に見る）
- 比較軸3: プラン初期選択（月額 / 年額。別途 ippei-shimizu/buzzbase#557 で月額デフォルトへ変更予定）

判定は Phase 0 で定義した CVR を使い、表示回数が少ないバリアントは除外する。

## 7. リスク

| リスク | 対応 |
| ---- | ---- |
| **登録直後の Paywall が記録フロー開始を妨げる** | 最大のリスク。現状は登録 → 記録フロー開始が 96.9%（90日コホート）で、ここは数少ない健全な区間。すべての画面をスキップ可能にし、`onboarding step viewed` / `profile setup completed`（ippei-shimizu/buzzbase#625）と併せて記録フロー開始率を監視する。悪化したら配置を撤回する |
| 価値未体験で加入した層の解約が早い | 実績としてトライアル3件のうち2件が37時間・5日で解約している。主指標はトライアル開始のままだが、**トライアル → 有料転換率を必ず併せて見る**。ここが極端に低ければリーチを増やしても売上にならず、ストアの指標だけ悪化する |
| 登録前オンボーディングで Pro 機能を見せると期待外れになる | 登録前の3スライドには Pro 専用機能の図を使わない。`artPrimitives` の共通部品だけ流用し、訴求は無料機能に限定する |
| 各ステップでの離脱位置が分からない | `paywall dismissed` の `step` 別分布を見て、離脱が集中するステップを削る |
| 中高生が決済手段を持たない | 主指標をトライアル開始に置く。保護者との共有を想定した文言（App Store のファミリー共有は月額プランで「オンにする」が未設定）は別途検討 |
| 参考記事のデータが自社と条件が違う | グローバル・多ジャンルの集計値なので、そのまま当てはめず A/B で自社検証する |

## 8. 決定事項

2026-08-27 時点で以下を確定した。

| 論点 | 決定 | 補足 |
| ---- | ---- | ---- |
| ステップ2の訴求項目 | 成績の深掘り分析 / 目標管理・振り返り / 練習記録・野球ノート の3項目 | 広告非表示は表示順序の問題で除外 |
| front（Web）の対応 | mobile 先行 | 課金の中心が iOS のため。効果を確認してから front へ展開する |
| 自動表示のトリガー | 初回記録完了時のみ | まず1箇所で検証し、データを見てから増やすか判断する |

2026-09-24 時点で以下を追加・変更した。

| 論点 | 決定 | 補足 |
| ---- | ---- | ---- |
| Paywall のステップ数 | 3ステップ案から2ステップ（価値 / プラン）へ変更 | 比較表を独立ステップにすると、無関係な行を読ませる画面を1枚増やすことになるためアコーディオンへ格納した |
| ステップ2の訴求項目 | トリガーと同系統の機能を最大3件に変更 | 実利用データ上、練習・目標・ノート系は閲覧者の大半に無関係。固定3項目をやめ、トリガー起点で出し分ける |
| ヒーローの見せ方 | 本人の成績データ（無ければサンプル） | 打球方向データ保有が1,282人おり、汎用の説明文より強い証明になる |
| 1画面型のバリアント保持 | 残さない | 1画面型のプラン到達率が低く、A/B の母数を確保できない |
| 表示形式 | シート型から全画面へ | シート型は画面下部が背景に取られ、分析の図を大きく見せられない |
| 機能紹介 | 見出し直下にスライドショーを置く | 文字だけの訴求では「何ができるか」が伝わらない |
| スライドの図 | 作り物のイラストのみ（本人データ・実カードは使わない） | Paywall で本物の分析を描くと未加入のまま中身が見え、ゲートが成立しない |

2026-09-26 時点で以下を追加・変更した。

| 論点 | 決定 | 補足 |
| ---- | ---- | ---- |
| 自動表示 Paywall の配置 | 初回記録完了直後 → **登録直後（ユーザー名登録の直後）** へ変更 | 初回記録直後のリーチは登録者の約48%に留まる。登録直後ならほぼ全員に届く。参考記事の数字もこの配置のもの |
| 初回記録直後の Paywall | **実装しない** | 初日に2回見せることになるため一本化する。`summary.tsx` の割り込みは現状のまま |
| Paywall を登録前オンボーディングに置くか | 置かない | RevenueCat の匿名 `app_user_id` を back の `UserResolver` が解決できず、購入しても entitlement が付与されない |
| 訴求のパーソナライズ | `profile-setup` の回答でスライド順を並べ替える | `PaywallSlides#orderSlides` の既存機構を流用する。投手なら球種別・コース別、打者なら方向別・カウント別を先頭に |
| `no_ads` の訴求 | この配置では含める | 閉じた直後に広告が出る順序にならないため、初回記録直後で除外した理由が当てはまらない |
| 登録前オンボーディング3スライド | Pro 機能の図は使わず `artPrimitives` の共通部品で描き直す | 登録前に見せた機能が登録後にロックされていると期待外れになり、健全な登録CVR（80〜87%）を損なう |
| 登録前オンボーディングの枚数 | 3枚のまま | 参考記事も2〜3画面。登録前が担うのは価値提案のみ |
